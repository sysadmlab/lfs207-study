# Why this happened  
While researching why this happened, I come to know of the underlying system design. </br>  
  
  If a user who is **NOT** **root** (elevated privileges) changes the permissions of a file or directory, and that user is not a member of its group, the kernel removes the SGID bit.  
  The command **setfacl** counts as changing permissions, hence the SGID is removed.

# How this applies to my work  
Throughout the demonstration, I applied the permissions using my user account **as**. My account was **NOT** part of the **ithelpdesk** or the **accounting** groups.  
Hence, the Linux Kernel removed the **Set GID** special permissions the moment I executed the **setacl** command.
