# Why this happened  
While researching why this happened, I learnt about the underlying system design - something I never knew before. </br>  
  
  If a user who is **NOT** **root** (elevated privileges) changes the permissions of a file or directory, and that user is not a member of its group, the kernel removes the SGID bit.  
  The command **setfacl** counts as changing permissions, hence the SGID is removed. </br>  

# How this applies to my work  
Throughout the demonstration, I applied the permissions using my user account **as**. My account was **NOT** part of the **ithelpdesk** or the **accounting** groups.  
I was the **User Owner** of all the directories.  
I only belonged to my **UPG** and the group **public**.  
Hence, the Linux Kernel removed the **Set GID** special permissions the moment I executed the **setfacl** command. </br>  

# What could have been done better  
Option 1. I could have executed all the commands with elevated privileges. </br>  
Option 2. Even when I started I MUST NOT have taken ownership of the directories. </br>  
<img width="499" height="156" alt="image" src="https://github.com/user-attachments/assets/8bd77df2-0909-46ff-8b63-bc61665719a3" /> </br>  
I MUST have let **root** be the **User Owner** of the directories and the respective **group accounts** (accounts, ithelpdesk) be the **Group Owner**. </br>  
If I had done this, I would have been forced to execute the commands using the **sudo** privileges and the **Set GID** special permissions would have stayed. </br>  

# Lesson Learnt  
For shared directories, I am going to let **root** be the **User Owner** and the respective **groups** be the **Group Owner**. </br>
